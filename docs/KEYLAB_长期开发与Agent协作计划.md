## 当前优先任务：迈从 Ace 68 GT 银羽视觉研究

- 用户确认以 Ace 68 GT 银羽为参考。官方图片显示银色外壳、透明键帽及紧凑 68 键布局；[官方商品资料](https://www.mchose.store/products/mchose-ace-68-gt-full-aluminum-esports-hall-effect-keyboard)。官方图片仅用于研究，不随项目分发。
- 当前工作台支持 61、81、87、104 键。`/parts/ace68` 已有独立的 68 键程序化外观初版，不是工作台模板；保留已有组装与方案数据，不把 75% 模板标成 68 键。
- 初版支持旋转、缩放、平移、逐键选择和拆解；内部层为示意，不推断真实配件兼容性。商城的 Ace 68 GT 商品卡可以进入该预览。
- 视觉质量仍未验收：当前模型透明材质、边框轮廓、侧面与细节和参考图存在差距。基于俯视参考与斜视渲染的自动轮廓检查未通过；两者视角、画幅及背景不同，不能据此判断精确相似度。后续需取得侧面与背面参考，匹配视角后重新比较并完成多角度验证。
- 推荐 Blender 制作和编辑可分层模型，使用其 [glTF 2.0 导出器](https://docs.blender.org/manual/en/latest/addons/scene_gltf2.html)导出 GLB；需要压缩时可评估 [glTF Transform](https://gltf-transform.dev/cli)。实际复用任何图片、模型或插件前核对许可。

## 1. 项目目标与本阶段边界

KEYLAB 面向想购买和搭配游戏外设的玩家，以精美的键盘 3D 外观 DIY 为核心，逐步发展为包含成品键盘、鼠标和耳机搭配、职业选手方案以及社区分享的外设选择平台。首批面向中国大陆，使用中文和人民币；电脑端优先，手机端保证浏览、社区与必要操作。产品视觉以深色科技风、紫色强调和键盘主体为核心；参照资料见 `tu/ck/`，实际素材授权以逐项核验结果为准。

**首个目标：小范围公开测试的完整体验。** 3D 键盘视觉与真实商品资料同步推进，串起外设搭配、职业选手方案和社区基础互动。首批允许可信真实资料与明确标记的演示资料并存；已有组装、购买清单、模拟购物车和云端方案代码应保留。

本次工作仅更新计划与项目规则，功能实现、远端变更和部署按后续具体任务及已有授权执行；此前“不擅自创建或删除数据库表”的要求继续有效。当前不开发真实支付、订单、结算或复杂商城后台；盈利和商城是后续方向。

指令优先级：用户最新明确要求 > 项目 `AGENTS.md` > 本计划 > 原始 PRD。出现冲突时，记录原因并遵循更高优先级的指令；本计划不能自动授权远程数据库写入、生产部署或其他超出当前任务范围的行为。

## 3. 不可破坏的产品规则

1. 3D 必须是真实 Canvas：支持旋转、缩放、平移、爆炸与合体、选中和回退；静态图片不能冒充交互模型。
2. 槽位使用稳定的 `Slot` 标识；点击和拖拽走同一兼容规则。`incompatible` 阻止安装；`unknown` 显示未验证；`warning` 显示原因。
3. 同一配列名称不构成 PCB、外壳和定位板可安装的充分证据；适配需要具体尺寸、接口和规则。
4. 商品、规格、规则和价格来自数据层；真实与演示数据明确区分。缺少真实品牌、价格、库存或链接时不得编造。
5. 金额以整数分存储；缺价为 `null` 并明确提示。第三方跳转仅使用实际配置、验证过的商品 URL。
6. 保存和迁移不得静默丢失逐键设计、图片或既有方案；恢复后重新计算兼容性和价格。
7. 无模型、无 WebGL、无网络、配置错误、空数据、数据库失败与缺少规格都要有可理解的状态和可用的降级路径。
8. 键盘外观调整以视觉预览为主；成品键盘外壳、键帽更换不等同实际购买或安装兼容。保留现有内部组装与兼容性能力。
9. 职业选手资料保留来源与最后核验时间；无法核实的信息标为待核验，不编造实时数据、选手配置或购买渠道。
10. 社区首版允许游客浏览；登录后图文发布、互动和举报，设备清单可选。公开测试需真实云端保存及基础内容管理，不把本地模拟当成云端验收。
11. 当前不开发真实订单、支付或结算；已有演示交易流程仅保持可运行。

## 4. 架构与职责

```text
Next.js 页面 / DOM 面板 ──> 目录数据层 ──> 统一 Supabase Client ──> Supabase Data API
              │                    └──────> 明确标记的本地演示数据
              ├──> Zustand 状态 ──> 兼容性引擎 / 价格计算
              ├──> R3F 场景 ──> 程序化零件 / 经授权 GLB / 回退
              └──> IndexedDB / localStorage 兼容 / 可选云端方案
计划中：外设搭配与选手内容 ──> 可信资料 / 表格导入 / 数据访问层
计划中：社区 ──> 邮箱身份 / 图文与互动数据 / 图片存储 / 基础管理
```

| --- | --- | --- |

## 5. 分阶段路线图

状态含义：`已实现演示` 不等于生产可用；`待处理` 是后续任务；`候选` 不自动进入当前范围。各阶段按依赖和验收推进，不承诺日程。

### P0｜基线与安全（进行中）

- **目标**：让后续开发可复现，保护已有工作和环境配置。
- **任务**：确认 Node/pnpm、锁文件、`.env.local` 忽略规则；核对页面、未提交改动和检查命令；修订并持续维护本计划。
- **验收**：不输出或提交密钥；记录仓库状态和实际执行结果；保留当前可运行流程。

### P1｜完整演示：视觉与数据并行（待处理）

- **目标**：同时改善视觉与数据，串起键盘外观 DIY、成品键盘预览、键鼠耳机搭配、选手方案和社区最小流程，形成可宣传和试用的演示。
- **视觉线**：用户先自行制作几个键盘演示模型；集成前核对可用格式、坐标、节点及使用授权。优先改善外壳、键帽和配色预览；未真实还原的商品明确标注示意，成品键盘更换只表示视觉效果。
- **数据线**：先设计商品与选手资料的表格模板，区分真实和演示；商品包含名称、品牌、分类、图片、参考价格、规格、来源与核验时间，有可靠购买 URL 时才显示链接。没有价格或链接保留缺失状态。
- **内容线**：展示键盘、鼠标和耳机的搭配，以及少量职业选手方案。首批游戏方向为《无畏契约》、三角洲行动、英雄联盟（LOL）、CS2 和绝地求生；具体选手与资料由真实来源决定。
- **社区线**：规划游客浏览、邮箱登录、图文发布、可选设备清单、点赞、收藏、评论、举报和隐藏违规内容；演示阶段的模拟状态必须明确标注。
- **验收**：键盘 3D 可交互，用户能看到并体验外观变化；外设方案和社区最小流程可演示；真实与演示、示意模型及缺价均可区分。此阶段的模拟体验不等同真实云端保存或公开测试验收。

### P2｜真实数据与云端能力（待处理，与 P1 协同）

- 首先只读检查目标 Supabase 的现有表、字段、关联、Data API、GRANT 和 RLS，区分表缺失、未暴露、权限问题及网络错误；不凭猜测对远端执行迁移。
- 梳理 `products`、`brands`、`categories`、`product_specs`、`product_models`、`product_offers`、`merchants` 与 `compatibility_rules` 的现有依赖，设计商品和规则读取状态解耦；缺规则仍是未验证。
- 根据检查结果，准备表格导入、邮箱身份、图文帖子、图片、设备清单、互动、举报及管理的数据与权限方案。保留现有本地方案和旧数据；迁移草案与远端操作按授权和隔离环境验证。
- 真实商品与选手资料先使用表格录入、审核和导入；自动同步属于后续扩展。每条选手方案记录来源、最后核验时间和待核验状态，不能承诺不存在的数据源实时更新。
- **验收**：商品查询、邮箱登录、帖子图片和互动在目标测试环境真实保存并可跨设备恢复；游客和不同用户的权限隔离已验证；来源、缺价、空表与连接失败有明确状态。
- **依赖/阻塞**：目标项目结构与授权、邮件及图片存储配置、可用的真实数据和素材；不足时提供可审阅方案并记录待办，不谎称线上完成。

### P3｜小范围公开测试（待处理，依赖 P1 与 P2）

- 验证桌面端 3D 外观调整，手机端浏览、社区和必要操作；图片与模型加载失败、网络异常均有可理解的提示或回退。
- 验证商品资料与参考价格、选手方案来源和核验时间、发布图文及可选设备清单、点赞收藏评论、举报及平台隐藏内容。
- 测试账号和内容必须保存在真实云端并可跨设备访问；在开放真实用户前完成身份、权限、内容管理、数据备份与部署检查。
- **验收**：真实用户可完成上述流程，演示数据与视觉预览明确标注；有测试记录、已知限制和反馈收集方式。不开发真实支付和订单。

### P4｜持续扩展与质量提升（待处理）

- 按反馈逐步补充精细键盘模型、可信商品和选手资料、可获授权的数据同步与更完整的手机体验。
- 保留并逐步完善已有内部结构、爆炸、拖拽、兼容性和键帽工坊；维护四种配列、旧方案及图片存储可靠性。
- 建立 GLB 资产约定：授权、来源、坐标、单位、尺寸、节点、材质、性能、版本与回退；素材按项核实，程序化模型不冒充真实商品。
- **验收**：四配列与已有方案不回退；点击和拖拽使用相同规则；明确冲突不可安装，未知明确提示；模型加载或存储失败有恢复路径。

### P5｜商城与盈利探索（候选，需后续明确范围）

- 根据实际测试和业务需求再讨论商城模式、合作渠道、订单或支付；分别明确产品、运营、技术和权限要求后开展。
- 测试阶段已需要基本的部署、回滚、备份、监控、安全和内容管理；不要等到商城阶段才考虑。
- 性能先测量加载、内存、3D 帧率和查询耗时，再根据设备与业务目标设预算；不凭空宣称达标。
- **验收**：未来功能以单独确定的范围和验收标准为准。

## 6. 数据与 Supabase 约定

### 商品模型与来源

- 商品核心属性、规格、模型和报价分层管理，产品标识与槽位标识保持稳定；必要时为字段保留来源、验证时间及演示标记。
- 应用读取层是边界：UI 不拼装 SQL，也不自行推断兼容关系。结构调整先明确旧方案、关联查询及兼容引擎的迁移影响。
- 价格为整数分；缺价使用 `null`；报价和商家是一对可追溯的数据。无有效链接时展示不可跳转状态。
- 当前种子脚本是演示资料；未经核实不能转为真实商品。全量迁移脚本不应在未知结构或已有数据的远端盲目执行。
- 首批资料使用统一表格整理和审核导入；商品记录真实/演示、来源及核验时间，参考价格可缺失，购买链接可缺失。选手方案记录游戏、选手、外设、来源、最后核验时间及待核验状态；不将演示选手配置标为真实。
- 社区帖子为图文内容，设备清单由用户选择是否附上；清单与可恢复 DIY 配置的关联不作为首版必需条件。真实用户的数据、图片和互动需要在云端持久化，不能只依赖浏览器本地存储。

### 访问与安全

- 浏览器只使用 publishable key 或兼容的旧版 anon key。`NEXT_PUBLIC_` 值会进入前端代码；secret/service-role、数据库密码和访问令牌不得写入前端、日志、仓库或聊天。
- 商品公开读取须分别检查 Data API 暴露、数据库 GRANT 与 RLS；只开放确需公开的上架资料。社区的公开帖子、用户操作、图片、举报和管理权限须按经审核的访问模型隔离，不能让普通用户获得管理员权限。
- 更改数据库前加载 Supabase 和 Postgres 相关技能，核对当前官方文档；先审阅结构、备份/回退和权限，再在隔离环境验证。不得使用 destructive reset 测试真实项目。
- 诊断只能输出必要的状态、受控错误分类和测试结果，不输出密钥、请求头、连接串或用户隐私。使用 `pnpm check:supabase` 做只读商品表检查；该检查不证明全部关联查询可用。
- 参考：[Supabase Data API 安全](https://supabase.com/docs/guides/api/securing-your-api)、[API keys](https://supabase.com/docs/guides/getting-started/api-keys)、[Postgres 文档](https://www.postgresql.org/docs/current/)。

## 7. 验证与交付标准

每个任务按影响范围提供可复现的检查与结果，遵循 `AGENTS.md`。默认检查：

```powershell
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm test:e2e
```

需要真实 Supabase 连接时，另运行 `pnpm check:supabase` 并说明是否仅测试了 `products`。浏览器测试会隔离真实目录请求并验证演示回退；不得把模拟结果说成真实数据库验收。若本机 PowerShell 找不到 pnpm，可使用 `start.cmd` 启动应用；开发检查应先安装并配置 pnpm，或使用现有可信的运行时路径。

| 变更范围 | 至少覆盖 |
| --- | --- |
| 商品读取 | 配置缺失、空表、拒绝访问、网络异常、真实/演示标记、图片/链接与缺价。 |
| 兼容与价格 | 兼容、冲突、未知、警告、缺价、多报价、规则缺失、不同安装入口一致。 |
| 3D 与组装 | 四配列、拖拽合法目标、冲突阻止、视角及爆炸切换、资源加载失败和 WebGL 降级。 |
| 工坊与保存 | 图片贴图、2D/3D 对应、导出导入、配列迁移、旧方案、损坏数据、存储失败。 |
| 外设与选手方案 | 键鼠耳机组合、真实/演示区分、来源及最后核验时间、缺失资料和过期待核验状态。 |
| 社区与云端 | 游客浏览、邮箱登录、图文及可选清单、跨设备保存、点赞收藏评论、举报、管理隐藏和权限隔离。 |
| 数据库与安全 | 在隔离环境测试 schema、RLS、权限及数据完整性；有条件时再只读验证目标项目。 |
| 页面体验 | 桌面与窄屏、加载与空态、键盘可达性；记录浏览器控制台错误和已知警告。 |

检查失败须写出失败命令、原因和实际影响；不得用未运行的测试或模拟数据替代线上验证。

## 8. Agent 接手与协作协议

### 开始工作

1. 阅读 `AGENTS.md`、本计划、`README.md` 以及相关模块；涉及 Next.js 修改先阅读本地 `node_modules/next/dist/docs/` 对应指南。
2. 运行 `git status --short --branch`，识别已有用户改动和未跟踪素材；不要把未提交内容当成可覆盖的垃圾。
3. 明确目标、输入、输出、限制、影响模块和验收命令；优先小步修改并复用代码。涉及线上项目时确认目标与当前授权，遵循只读边界。
4. 协作或并行工作仅在用户或适用规则授权时进行；按文件或模块划定负责人，避免多个 agent 同时编辑同一文件。发现重叠先协调，再继续。

### 完成任务

交付时说明目标与范围、修改文件、关键行为、运行的检查及结果、未完成事项和下一步。涉及数据源或资源时，写清是演示/真实、模拟/远端、已核实/待核实。不要提交其他人的改动或环境文件；提交、推送、部署和远端写入遵循用户在当前会话中的授权。

可复制的交接模板：

已运行命令与结果：

### 需要用户逐步提供的资料

- 自行制作的首批键盘演示模型，以及对应的外壳、键帽、配色参考；提供模型格式、尺寸、可用范围和已知限制。后续再补充经授权的精细模型与商品图片。
- 可使用的商品与职业选手资料来源，以及已有表格或接口信息；优先覆盖首批热门游戏、键盘、鼠标和耳机。采集或使用前逐项核实授权，不提供的价格、链接和适配信息保持缺失。
- 小范围测试使用的 Supabase 项目及其可用配置、邮件登录和图片存储条件；不在聊天、日志或仓库中提供 secret/service-role、数据库密码或访问令牌。
- 首批测试范围、内容管理负责人和公开测试所需的部署条件；具体选手名单和更新频率由可用的可靠来源决定。
